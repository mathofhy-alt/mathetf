# 33개 개선 항목 현재 상태

## 2026-09-23 별도 Supabase 테스트 프로젝트

- 무료 조직 `mathetf-staging` 아래 프로젝트 `fnamfsijayavwakvgzaf`를 생성했다. 운영 프로젝트와 분리되어 있으며 GitHub 저장소는 연결되지 않았다. `main PRODUCTION`은 이 테스트 프로젝트 내부의 기본 브랜치 표시다.
- 실제 회원·결제·문항 데이터는 복사하지 않았다. 기능 검증에 필요한 최소 표 8개를 만들고, 사용자가 `tests/staging-migrations-20260923.sql`의 신규 SQL 4개를 이 프로젝트에 적용했다. 기본 표를 포함한 `public` 표는 11개다. 이는 운영 DB 전체 복제가 아니다.
- 실제 Supabase에서 신규 결제·수익·출제 이벤트 표의 RLS를 확인했다. 익명 사용자의 주문 조회와 익명·회원의 결제 완료 함수 실행은 금지, 서버 역할의 실행은 허용된다. 시험지 저장 함수도 서버 역할만 실행 가능하다.
- 가상 문항 1개로 범위 검색·제외·필터 집계·자동 출제를 검사했다. 가상 주문은 첫 처리 1회와 재호출의 중복 방지, 30포인트 사용, 70% 제보자 적립 및 단일 구매 기록을 확인했다. 다른 사람 폴더 저장 차단, 시험지 20개 상한, 저장 이벤트의 서버 기록도 확인했다. 모두 트랜잭션을 되돌렸고, 관련 가상 사용자·문항·주문·기록이 0건 남은 것을 재조회했다.
- 사용자가 포인트 유료 충전 기능을 진행하지 않기로 했다고 정정했다. 격리 작업본에서 충전 페이지·모달을 제거하고 신규 주문 API는 자료 구매(`cart`)만 받도록 바꿨다. 기존 보유·적립 포인트와 과거 결제 결과 처리 코드는 유지한다. `READY` 같은 진행 중 자료 결제는 기존 주문을 보존하여 두 번째 결제를 시작하지 않도록 수정했다.
- 사용자가 현재 홈페이지의 포트원 채널이 `실연동`임을 확인했다. 이를 테스트 결제에 사용하지 않는다. 격리 작업본에 `tests/portone-staging.cjs`와 설정 예시를 추가했으며, 이 실행기는 별도 Supabase 프로젝트와 확인된 KG 테스트 채널만 허용한다. 테스트 프로젝트의 공개 키·서버 키 두 개를 로컬 비공개 파일에 설정해야 실행할 수 있고, 기존 포트원 상점·서버 키는 원본 환경파일에서 읽기 전용으로 가져온다.
- 사용자가 로컬 비공개 파일에 테스트 프로젝트 키를 입력했다. 충전 기능 취소 결정 이전에 만든 1,100원 테스트 주문은 포트원 상태 `READY`였고 PG 창이 로딩 상태로 멈춰 승인되지 않았다. 테스트 DB의 포인트와 결제 기록은 0, 주문은 `pending`이었다. 이 주문으로 추가 결제를 진행하지 않는다. 자료 직접 구매의 실제 PG 승인은 별도로 검증해야 한다. 운영 회원·결제에는 영향이 없다.
- 테스트 DB에 가상 PDF 1개와 전용 계정의 장바구니 항목 1개를 추가했다. 로컬 구매 화면에서 1,100원 자료가 표시됐고, 인증된 장바구니 조회·자료 직접 구매 주문 생성이 성공했다. 생성 주문은 결제창을 열지 않고 즉시 삭제했다. 같은 계정의 포인트 충전 주문 요청은 HTTP 400으로 거부됐다. 테스트용 가상 PDF에는 실제 파일이 없어 다운로드 검사용 자료가 아니다.
- 포트원 공식 KG이니시스 안내(https://help.portone.io/content/inicis)에 따르면 테스트 모드도 실제 출금 후 매일 23:00~23:50에 자동 취소된다. 실제 카드 승인 시험은 사용자에게 이 사실과 1,100원 금액을 알리고 결제 여부를 결정받기 전에는 진행하지 않는다.
- 결제사 실제 테스트 승인·중단·모바일 복귀, 앱을 테스트 프로젝트에 직접 연결한 인증·Storage 전체 흐름은 아직 검증하지 않았다. 지금 결과만으로 운영 배포 준비 완료라고 주장하지 않는다.
- 사용자가 배포 시 “이거 GitHub 삭제”를 요청했다. 현재 테스트 프로젝트에는 연결된 GitHub 저장소가 없다. 기존 `mathofhy-alt/mathetf` 저장소를 삭제하라는 뜻인지 단정하지 말고, 배포 단계에서 정확한 정리 대상을 확인한다. 저장소나 운영 연결은 지금 삭제하지 않는다.

## 2026-09-23 배포 전 운영 DB 읽기 전용 대조

- 운영 `questions`에는 새 검색 함수가 요구하는 컬럼이 모두 있습니다. 기존 `payment_history`와 `purchased_items`에 새 `order-` 번호를 쓰는 기록은 0건입니다.
- 운영에는 새 기능용 `payment_orders`, `question_bank_events`가 아직 없으며 이는 미적용 SQL 4개가 만들 예정입니다. 추가로 기존 코드가 참조하는 `submission_earnings`도 없음을 발견해 `202609200002_payment_orders.sql`에 생성·본인 조회 권한을 포함했습니다.
- 운영 `exam_materials`에는 `source_submission_id`가 없습니다. 신규 주문 코드는 명시적 연결이 없으면 원본 제보를 기존 시험 정보로 대조하고, 후보가 여러 개면 주문을 중단합니다. 임의로 제보자를 선택하지 않습니다.
- 기존 로컬 검사 DB에는 이 수익 기록 표가 미리 있어 누락을 감추고 있었습니다. 검사 DB에서 미리 만든 표를 제거하고 SQL 4개가 직접 생성하게 수정한 뒤 결제·권한 회귀 검사 16개를 다시 실행해 모두 통과했습니다. 운영 DB 변경이나 실제 결제는 하지 않았습니다.
- 별도 Supabase 프로젝트에서 신규 SQL의 권한·기능 검증은 통과했습니다. 실제 앱 인증·Storage·결제사 통합 검증은 남아 있습니다.
- 2026-09-23 읽기 전용 운영 재점검에서 기존 필수 표 8개의 컬럼이 확인됐고 새 결제·수익·출제 이벤트 표 3개는 아직 없으며 `order-` 번호의 결제·구매 기록은 각 0건입니다. 취소된 포인트 충전은 신규 운영 주문 스키마에서도 거부하도록 바꿨습니다. [운영 DB 배포 전 실행안](운영DB-배포전-실행안.md)과 단일 트랜잭션 SQL을 준비했으나 운영 DB에는 실행하지 않았습니다.

## 운영 검증 단계의 선행 조건

현재 검토 서버는 모의 인증·DB·저장을 쓰며 실제 결제와 외부 AI 연결을 차단합니다. 이 상태에서 실결제사·인증·Storage 통합을 완료했다고 처리할 수 없습니다.

1. 운영과 분리된 테스트 DB·Storage·인증 환경에서 신규 SQL과 기존 정책을 함께 적용하고 역할별 접근을 확인합니다. 이번 로컬 권한 검사는 이를 대체하지 않습니다.
2. 결제사 테스트 설정에서 결제 승인·취소/중단·모바일 복귀·중복 요청을 확인합니다. 운영 결제나 포인트 변경은 하지 않았습니다.
3. 한글 앱과 실제 모바일 기기를 사용할 수 있는 환경에서 파일 조판과 다운로드를 확인합니다. 현재 이 작업의 도구에는 한글 앱 조판 기능이 없습니다.
4. 실제 인식·추천 서비스와 문항 원본을 연결한 격리 환경에서 결과 품질을 확인합니다.
5. 배포 검토를 마친 뒤 검색엔진과 계측 상태를 확인합니다. 광고는 별도 예산 승인 후 실행합니다.

목적별 새 영상은 완성 상태가 아닙니다. 현재 제공물은 단계별 화면 안내와 가이드입니다.
